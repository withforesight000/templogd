# AGENTS.md

## Repository overview

This is a Rust 2024 workspace for collecting and serving Nature Remo ambient-sensor data.

- `templogd`: polls the Nature Remo API every 30 seconds and writes readings to Redis Streams.
- `tempgrpcd`: serves readings over an authenticated gRPC API and optionally samples them with a Redis Lua function.
- `common`: shared domain models, repository traits, HTTP/Redis adapters, and logging support.

The normal data path is Nature Remo -> `templogd` -> Redis stream `ambient_condition` -> `tempgrpcd` -> gRPC client. Temperature, humidity, and illumination are stored as stream fields. The two binaries communicate with their datastore workers through bounded Tokio MPSC channels and shut down through `CancellationToken`.

## Important files and boundaries

- Workspace dependencies and release settings: `Cargo.toml`
- Local/container usage and environment variables: `README.md`, `compose.yml`
- Shared domain contracts: `common/src/model/repository/`
- Concrete external-system adapters: `common/src/gateway/` and `common/src/infra/`
- Daemon orchestration: `templogd/src/infra/tasks.rs`
- gRPC composition, authentication, reflection, and Redis function loading: `tempgrpcd/src/infra/server.rs`
- Request validation: `tempgrpcd/src/validator/`
- Sampling implementation: `tempgrpcd/templates/xrange_with_sampling.lua.j2`
- CI source of truth: `.github/workflows/ci.yml`

Keep dependency direction toward domain contracts: controllers call use cases, use cases depend on repository/port traits, and infrastructure supplies concrete implementations. Put code shared by both services in `common`; keep service-specific behavior in its service crate.

The protobuf Rust types come from the Git dependency `tempgrpcd-protos` in `tempgrpcd/Cargo.toml`. There are no protobuf source files in this repository. Do not hand-edit generated types or assume the example proto path in the README exists locally.

## Development commands

Prerequisites are a current stable Rust toolchain with Rust 2024 support and `protoc`. Redis 7.x is required for running the services, but the existing unit tests use mocks/stubs and should not require a live Redis instance.

Run the same checks as CI before handing off changes:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features --no-fail-fast
```

During iteration, prefer a focused test first, for example:

```sh
cargo test -p common
cargo test -p templogd
cargo test -p tempgrpcd
cargo test -p tempgrpcd validator::get_ambient_conditions_request::tests
```

Apply formatting with `cargo fmt --all`. Build release binaries with `cargo build --release`. Run the complete local stack with `docker compose up --build`; replace the `XXX` credentials in `compose.yml` locally and never commit real tokens.

## Runtime configuration

Both binaries use Clap, so settings can be passed as long options or environment variables.

- `templogd` requires `TEMPLOGD_NATURE_REMO_API_TOKEN`, `TEMPLOGD_NATURE_REMO_DEVICE_ID`, and `TEMPLOGD_REDIS_HOST`; `TEMPLOGD_REDIS_PORT` defaults to `6379`.
- `tempgrpcd` requires `TEMPGRPCD_SERVER_BIND_ADDRESS`, `TEMPGRPCD_SERVER_PORT`, `TEMPGRPCD_BEARER_TOKEN`, and `TEMPGRPCD_REDIS_HOST`; `TEMPGRPCD_REDIS_PORT` defaults to `6379`.

Never log or expose bearer/API tokens. Preserve the masked `Debug` behavior of configuration structs. The gRPC authorization metadata must have the exact form `Bearer <token>`.

## Code and test conventions

- Follow `rustfmt.toml` (4-space indentation, 120-column maximum).
- Keep async I/O on Tokio and propagate cancellation when adding long-running work.
- Preserve `Send`, `Sync`, and `'static` bounds required by spawned tasks and async repository traits.
- Treat the polling, datastore, and gRPC server tasks as critical process components. If one returns before
  cancellation, returns an error, or panics, cancel its siblings, await coordinated cleanup, and propagate a typed
  failure to `main` so the process exits unsuccessfully. Do not consume a `JoinError` only by logging it.
- Do not use `unwrap()` or `expect()` for fallible daemon startup work such as parsing bind addresses, connecting to
  Redis, rendering templates, or loading Redis functions. Preserve the underlying cause in a typed startup error.
- Use repository/port traits as seams for tests. Prefer deterministic in-process stubs or mocks over external API or Redis calls.
- Add tests next to the implementation in `#[cfg(test)] mod tests`. Unit tests must collectively execute every path at least once across both success and failure cases, including validation, error propagation, and shutdown paths affected by a change.
  - Code generated by external commands or code-generation tools is excluded from this coverage requirement.
  - Test private methods through public behavior wherever practical instead of calling them directly.
  - Direct tests of a private method are acceptable when its complexity makes comprehensive coverage through the public interface unreasonably difficult.
- Add Rustdoc comments (`///` or `//!`) to newly introduced methods and other callable APIs.
  - When modifying existing code, add Rustdoc if the method accepts a data structure whose shape or meaning is difficult to infer from its type, or if the method's purpose is not immediately clear.
  - Write documentation so a Rust beginner can understand the method's purpose, inputs, outputs, errors, and important side effects. The goal is to let responders focus on identifying and resolving an incident rather than first reverse-engineering complicated code.
- Never swallow errors. Add useful context by wrapping errors at the appropriate layer and propagate them to the caller.
- Use `thiserror` error types at layer boundaries. Preserve the original cause when wrapping errors, and convert domain/use-case failures to appropriate tonic `Status` values only in the gRPC-facing layer.
- Validate requests before dispatching to a use case. For `GetAmbientConditions`, both timestamps are required, start must not exceed end, and `samples`, when present, must be greater than zero.
- Preserve Redis compatibility: the stream key is `ambient_condition`; fields are `temperature`, `humidity`, and `illumination`; the sampling function is `xrange_with_sampling` and is loaded with replacement during `tempgrpcd` startup.
- Update the Lua template and its Rust call site/tests together if the sampling function signature changes. Redis Functions require Redis 7 or later.
- Use structured `tracing` instrumentation consistent with surrounding code. Avoid logging full request metadata, credentials, or other secrets.
- Tokio channel send failures can contain the unsent value. Do not format such failures with `?` or otherwise log the
  payload; record only safe channel and operation metadata.
- When work crosses an MPSC boundary, carry the originating span or trace ID when downstream logs must remain
  request-correlated. Instrument the external call and enter that span for completion, failure, and unsupported-operation
  logs. Do not describe operations without a request span as originating from gRPC.
- Record filterable operational values such as `signal`, `operation`, `reason`, and `task` as tracing fields instead of
  embedding them only in message text.
- Use stable span names in `<layer>.<method>` form, where `<layer>` is the clean-architecture layer or its source directory and `<method>` is the Rust method or function name. When a layer contains multiple external systems or implementations, use `<layer>.<component>.<method>` (for example, `gateway.redis.fetch_ambient_conditions` and `gateway.nature_remo.fetch_ambient_condition`). For manually created task or request spans, use the same structure with the operation name in the final segment. Use the actual method name `new` rather than suffixes such as `_new`, and apply the same convention to `info_span!` names.

## Change discipline

- Inspect `git status` before editing. The worktree may contain user changes; do not discard, rewrite, or include unrelated modifications.
- Keep `Cargo.lock` synchronized when dependencies change.
- Update `README.md` and `compose.yml` when CLI flags, environment variables, ports, or operational requirements change.
- When Compose explicitly enumerates a service's environment, add every new runtime setting there with a host
  pass-through or documented default, and verify both default and overridden values with `docker compose config`.
- Update or coordinate the external protobuf repository when changing the public gRPC schema; changing only this repository is insufficient.
- Do not weaken CI lint settings or silence warnings broadly. Fix the underlying warning or constrain an exception to the smallest justified scope.
- `cargo audit` runs weekly but is currently non-blocking; dependency changes should still be reviewed for advisories and unnecessary additions.
- Format commit messages as follows:
  - The first line must be a concise English sentence that starts with a capital letter and ends with a period.
  - Leave the second line blank.
  - From the third line onward, summarize the changes as a bullet list. The list may be omitted only for a very small change.
